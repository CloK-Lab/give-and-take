A buyer pays an agent for a service. Before considering what the service does,
we can ask a smaller question: where are the funds while the call is pending,
and what happens when it is settled or refunded?

We model one call between a buyer and a provider. Amounts are natural numbers in
one abstract accounting unit. Reserving a price makes those funds unavailable
to either participant until settlement or refund.

\begin{definition}[Accounted funds]

balances. Let $e(s)$ be the reserved price when the phase is reserved, and zero
otherwise. Define

$$
T(s) = b(s) + v(s) + e(s).

The reservation is stored once, inside the phase. This representation cannot
contain a finished call with a separate nonzero escrow balance.

\begin{definition}[Conservation]

## Executable transitions

The available actions are reserve, settle, and refund:

```lean4 file="./Model.lean" declaration="Action"
```

| Current phase | Action | Effect |
| --- | --- | --- |
| Ready | Reserve a price within the buyer's balance | Move that amount into the reservation |
| Reserved | Settle | Transfer the reservation to the provider |
| Reserved | Refund | Return the reservation to the buyer |
| Any | Any other action | Reject |

This is a pure interpreter. A rejected action makes the result `none`; that

## Work through an example

Start with buyer balance 100 and provider balance 20. Reserving 30 yields buyer
70, provider 20, and escrow 30. The next action chooses between two outcomes:

<Tabs labels={["Settle", "Refund"]}>
<Tab>

```lean4

-- some { buyer := 70, provider := 50, phase := .settled }
```

The provider receives the reserved 30. The accounted total remains 120.

</Tab>
<Tab>

```lean4
run (initial 100 20) [.reserve 30, .refund]
-- some { buyer := 100, provider := 20, phase := .refunded }
```

The buyer recovers the reserved 30. The balances are restored, while the refunded
phase records that this call is finished.

</Tab>
</Tabs>

`Checks.lean` also cover insufficient funds, repeated settlement, settlement
after refund, and a zero-price call.

## Why every successful execution conserves funds

\begin{theorem}[One action]

For every state $s$, action $a$, and resulting state $s'$, if
`execute s a = some s'`, then $T(s')=T(s)$.

\end{theorem}

\begin{proof}

There are three successful cases. Reservation subtracts a funded price from the
buyer and places it in escrow. Settlement moves escrow to the provider. Refund
moves it back to the buyer. Each preserves the sum. All other cases reject.

</CodePreview>

\end{proof}

\begin{theorem}[An action sequence]

For every state $s$, finite list of actions $A$, and state $s'$, if
`run s A = some s'`, then $T(s')=T(s)$.

\end{theorem}

\begin{proof}

Induct on the list of actions. The empty list leaves the state unchanged. For
a nonempty successful list, the first action preserves the total by the
one-action theorem, and the remaining list preserves it by induction.

## What to study next

The current model contains one call, no fees, and no external service or wallet.
It supplies no caller identities, delivery evidence, deadlines, or concurrency.
The accounting proofs alone therefore establish neither fair exchange nor
incentive compatibility.

Several extensions lead to distinct questions:

- **Authorization:** who may reserve, settle, or refund?
- **Delivery:** what evidence should permit settlement?
- **Nested calls:** can a provider fund another agent while its own payment is reserved?
- **Strategies:** which decisions maximize each participant's utility, and what
  can go wrong when those decisions interact?

The [payments topic](../../docs/topics/payments.md) connects these questions to
x402. The [agent interaction topic](../../docs/topics/agent-interaction.md)
considers task and delegation semantics. This case is a local model to build
understanding; protocol conformance remains a separate task.
